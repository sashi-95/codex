# Security Principles — セキュリティ原則 (全案件必須)

関連: [../delivery/delivery-methodology.md](../delivery/delivery-methodology.md)
位置づけ: 顧客向けにはこの内容を要約した「Security Overview」1枚を提案書に同梱する
(Phase 2で作成)。エンタープライズ商談ではセキュリティが最初の関門であり、
**この原則自体が営業資産**である。

## 1. データ保護

1. **顧客データを無断で外部AIサービスへ送らない**
   - LLM利用は事前に顧客へ明示し、書面合意を得る (SOWのデータ取扱条項)
   - 合意がある場合も、送信データを必要最小限にする (全件ではなくサンプル、実名ではなくマスク)
   - 顧客要件に応じて: API経由 (学習に使われない設定) / リージョン指定 / オンプレLLMの選択肢を提示
2. **顧客ごとのデータ分離**
   - 顧客案件は専用GitHubリポジトリ・専用フォルダ・専用認証情報。共有ストレージに混在させない
   - 案件終了時のデータ削除ポリシーを定義し、削除証明を出せるようにする
3. **個人情報・財務情報・認証情報をログに残さない**
   - ログ設計時にマスキング (PIIリダクション) を組み込む — 納品物のログも同様

## 2. 認証情報とアクセス

4. **APIキー・パスワードをソースコードに直接記載しない** — `.env` + シークレット管理。
   `.gitignore` に `.env` を必ず含め、コミット前フックで検知する
5. **最小権限**: Bot用アカウントは業務に必要な取引・スコープのみ。人間の個人アカウントを自動化に使わない
6. **本番と開発の分離**: 開発・検証は顧客のテスト環境で。本番アクセスはリリースフェーズのみ

## 3. 実行時の安全装置 (納品物の標準装備)

7. **操作ログの保持**: すべての自動実行は「いつ・何を・どのデータで・結果どうなったか」を記録
8. **Human-in-the-Loop**: 財務処理 (支払・転記)・データ削除・権限変更は原則人間の承認を挟む。
   金額等の閾値を顧客と合意し、承認履歴を残す
9. **読み戻し検証**: 書き込み系は実行後に別経路で読み直して突合する (転記ミスの構造的防止)
10. **ロールバック手順**: 全納品物に「戻し方」を文書化。戻せない操作は事前承認を必須にする
11. **手動代替手順**: 自動化が停止しても業務が止まらないよう、手動での実施手順を納品物に含める

## 4. 自社運用のセキュリティ

- 自社デバイス: ディスク暗号化 / パスワードマネージャ / 全サービスでMFA
- 顧客環境へのアクセスは顧客発行のアカウントで行い、共有アカウントを作らない
- 保険: E&O (Errors & Omissions) / サイバー保険をM2までに加入検討
- インシデント対応: 検知→顧客への第一報 (24時間以内)→影響範囲特定→対処→再発防止書、の手順を事前定義

## 5. 案件での適用チェックリスト (Solution Design時に必須)

- [ ] 扱うデータの分類 (PII/財務/認証情報の有無) を特定したか
- [ ] LLMへ送るデータと送らないデータを線引きし、顧客と合意したか
- [ ] Bot用アカウントと最小権限を顧客に依頼したか
- [ ] HITL承認ポイントと閾値を定義したか
- [ ] ログ・監査証跡の保存先と保持期間を決めたか
- [ ] ロールバック手順と手動代替手順を成果物リストに入れたか
