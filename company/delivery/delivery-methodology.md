# Delivery Methodology — 標準デリバリープロセス (15フェーズ)

関連: [../services/service-catalog.md](../services/service-catalog.md) /
[../security/security-principles.md](../security/security-principles.md)

すべての案件はこの15フェーズで進める。1〜8が営業〜契約 (Assessment含む)、
9〜15が実装〜保守。各フェーズは「完了条件を満たすまで次に進まない」ゲート制。
✋ = 顧客の承認ポイント。

---

### 1. Lead Qualification
- **目的**: ICP合致と支払い意思の見極め。追うべきリードに時間を集中する
- **入力**: リード情報 (会社・役職・接点の経緯)
- **実施作業**: ICP照合 / 企業調査 (規模・システム・ニュース) / 課題仮説の作成
- **成果物**: リード評価メモ (A/B/C格付けと仮説)
- **完了条件**: 格付けと次アクションが決まっている
- **リスク**: 調査に時間をかけすぎる → 1社15分上限

### 2. Discovery Call
- **目的**: 対象業務の特定と定量化 (6問: 時間/回数/実行者/エラー/削減/回収)
- **入力**: リード評価メモ
- **実施作業**: playbook §4の型で30分実施 / 直後にメモ構造化
- **成果物**: Discoveryメモ (業務候補・数値・決裁ルート・失格判定)
- **完了条件**: Assessment提案の可否判断ができる
- **リスク**: 雑談で終わる → 6問チェックリストを手元に置く
- ✋ **顧客承認**: Assessment実施の口頭合意

### 3. Process Assessment (有償 $3,000)
- **目的**: 自動化対象の確定と投資判断材料の提供
- **入力**: Discoveryメモ / ヒアリングアクセス / サンプルデータ
- **実施作業**: 担当者ヒアリング2-3回 / 業務の観察 (画面録画依頼) / 候補洗い出しと優先順位付け
- **成果物**: 業務候補リスト (工数・頻度・自動化難易度つき)
- **完了条件**: 対象業務1つを顧客と合意
- **リスク**: 候補が多すぎて絞れない → 「最も回収が早い1つ」を推奨として明記

### 4. Current-State Mapping
- **目的**: 選定業務のAs-Isを誰が見ても分かる形に固定する
- **入力**: ヒアリング記録 / 画面録画 / サンプルファイル
- **実施作業**: ステップ分解 (入力→判断→操作→出力) / 例外パターン列挙 / 関与者・システム・データの整理
- **成果物**: 現状業務マップ (ステップ表 + 例外一覧)
- **完了条件**: 担当者が「この通りです」と確認済み
- **リスク**: 例外の見落とし → 「月に1回でも起きる例外は?」を必ず聞く
- ✋ **顧客承認**: As-Isマップの内容確認

### 5. ROI Estimation
- **目的**: 投資回収の定量化。価格の正当化と導入後の効果測定基準
- **入力**: 現状業務マップ / 工数・単価データ
- **実施作業**: 削減時間試算 / エラーコスト試算 / 回収期間計算 (保守費込み)
- **成果物**: ROI試算シート (前提条件明記)
- **完了条件**: 顧客の数字 (自己申告) に基づいており、前提が文書化されている
- **リスク**: 過大な試算が後で信頼を毀損 → 保守的シナリオを併記

### 6. Solution Design
- **目的**: 技術構成の決定 (API / RPA / AI / RAGの使い分け)
- **入力**: 現状業務マップ / 顧客のシステム制約 / セキュリティ要件
- **実施作業**: 構成案作成 (既存テンプレート資産の流用判断) / HITL設計 / 非機能要件整理 / リスク分析
- **成果物**: ソリューション概要 (構成図・データフロー・承認ポイント・前提条件)
- **完了条件**: 14日で納品可能な設計であること (不可能なら分割提案に変換)
- **リスク**: 過剰設計 → 「Sprint 1回で動く最小構成」を強制

### 7. Proposal
- **目的**: 受注
- **入力**: Assessment Report (フェーズ3-6の統合)
- **実施作業**: 提案書作成 (課題→解決→ROI→計画→価格) / スコープ内外の明文化
- **成果物**: 提案書 + 見積書
- **完了条件**: Discovery後3営業日以内に送付
- **リスク**: スコープ曖昧 → 「含まれないもの」欄を必須に
- ✋ **顧客承認**: 提案受諾

### 8. Contract
- **目的**: 法的合意と前金受領
- **入力**: 提案書 / NDA・SOWテンプレート
- **実施作業**: SOW作成 / NDA締結 / 請求 (50%前金)
- **成果物**: 締結済みSOW / 入金確認
- **完了条件**: **前金入金確認後にのみ実装を開始する**
- **リスク**: 口約束で着手 → 例外なし
- ✋ **顧客承認**: SOW署名

### 9. Technical Discovery
- **目的**: 実装前の技術的前提の検証 (Sprint日程はここから起算)
- **入力**: システムアクセス権 / テスト環境 / サンプルデータ
- **実施作業**: 接続確認 (API/GUI/権限) / データ実物確認 / 画面ID記録 (SAP GUI案件) / 環境分離確認
- **成果物**: 技術検証メモ (接続OK/NG、判明した制約)
- **完了条件**: 主要な接続が実際に疎通している
- **リスク**: アクセス付与の遅延が納期を食う → SOWに「顧客のアクセス提供遅延は納期に加算」と明記

### 10. Prototype
- **目的**: 動くものを最速で顧客に見せ、方向を固定する
- **入力**: 技術検証メモ / ソリューション設計
- **実施作業**: コア機能実装 (テンプレート資産から開始) / 実データでの動作確認 / 中間デモ (Day 5前後)
- **成果物**: 動くプロトタイプ + デモ録画
- **完了条件**: 顧客が実データで動作を確認した
- **リスク**: 完璧主義で中間デモが遅れる → Day 5デモは品質不問で見せる
- ✋ **顧客承認**: プロトタイプ方向性の確認

### 11. User Acceptance Testing
- **目的**: 業務担当者による受け入れ確認
- **入力**: プロトタイプ / テストケース (正常系 + 例外系 + 異常系)
- **実施作業**: テストケース作成 / 担当者と実施 / 不具合修正 / 例外時の挙動確認
- **成果物**: UAT記録 (実施日・結果・修正履歴)
- **完了条件**: 全テストケース合格 + 残額請求
- **リスク**: UATで新要件が出る → スコープ外リストに記録し追加開発へ
- ✋ **顧客承認**: UAT合格サイン (残金50%の支払いトリガー)

### 12. Production Release
- **目的**: 本番稼働
- **入力**: UAT合格版 / 本番環境アクセス
- **実施作業**: 本番デプロイ / 監視設定 / ロールバック手順の最終確認 / 初回本番実行の立ち会い
- **成果物**: 本番稼働 / リリース記録 / ロールバック手順書
- **完了条件**: 本番データで1サイクル成功
- **リスク**: 本番特有のデータで初回失敗 → 初回は必ず立ち会い、HITLモードで開始
- ✋ **顧客承認**: 本番リリース判定

### 13. Hypercare (リリース後5営業日)
- **目的**: 初期トラブルの即応と定着
- **入力**: 本番稼働システム
- **実施作業**: 毎日の稼働確認 / 即日修正 / 利用者からの質問対応
- **成果物**: Hypercare日報 (簡潔に)
- **完了条件**: 連続3営業日の無障害稼働
- **リスク**: この期間の稼働をどう請求するか曖昧 → Sprint価格に含むと明記済み

### 14. Handover
- **目的**: 属人化の解消。顧客が自走できる状態にする
- **入力**: 全納品物
- **実施作業**: runbook整備 / 引き継ぎセッション (録画) / 管理者向け操作説明 / ソース・認証情報の引き渡し整理
- **成果物**: runbook / 引き継ぎ録画 / 納品物一覧 (何がどこにあるか)
- **完了条件**: 顧客側担当者が基本操作と障害時一次対応を実演できる
- ✋ **顧客承認**: 納品完了サイン → 保守契約の開始確認

### 15. Monthly Support (継続)
- **目的**: 安定稼働とアップセル (次の自動化候補の発見)
- **入力**: 保守契約 / 監視データ
- **実施作業**: 稼働監視 / 障害対応 / 月次レポート (稼働率・処理件数・削減時間の実測) / 改善提案
- **成果物**: 月次ヘルスレポート (**ROI実測値を必ず載せる** — 更新とアップセルの根拠)
- **完了条件**: 毎月のレポート送付と契約更新
- **リスク**: 保守が「何でも屋」化 → 契約時間枠を超える依頼はミニSprint見積に変換

---

## Sprint 14営業日の標準スケジュール

```
Day 1-2   Technical Discovery (フェーズ9)
Day 3-7   Prototype (Day 5: 中間デモ)
Day 8-10  UAT + 修正
Day 11-12 Production Release
Day 13-14 Hypercare開始 + Handover資料
(Hypercareの残りはDay 14以降5営業日)
```
