# バックオフィスAI 全体アーキテクチャ設計書

対象スタック: SAP BTP Joule / SAPオンプレ (VBS資産あり) / SharePoint Online /
Power Apps / Power Automate / Python / Cursor AI (開発IDE)

ゴール: **バックオフィス業務 (転記・照合・起票・レポート) を人間の代行レベルで
自律実行するAI** を、既存スタックの上に安全に構築する。

---

## 1. 基本思想: 各ツールの「正しい持ち場」

先に結論。全部をつなぐ中心は **Python製オーケストレーションランタイム** (自社開発) で、
他のツールはその周辺の「チャネル」「トリガー」「実行先」に配置する。

| ツール | 持ち場 | やらせないこと |
|---|---|---|
| **Python** | エージェント本体 (LLM判断 + ツール実行 + ガードレール + 監査)。全業務ロジックの集約点 | — |
| **SAPオンプレ** | 実行先 (転記のターゲット)。接続は RFC/BAPI・OData を第一選択 | GUI操作への依存を増やすこと |
| **既存VBS (GUIスクリプト)** | 過渡期のツールアダプタ。パラメータ化してPythonから呼ぶ | 新規業務をVBSで作ること |
| **SAP BTP Joule** | SAP画面内の「人間向け」対話チャネル。Joule Studioのカスタムスキルからエージェント基盤を呼ぶ | 業務自動化の本体をJoule内に作り込むこと |
| **SharePoint Online** | 書類の入出力 (請求書PDF・Excel台帳・成果物)、監査証跡の保管 | DB代わりの複雑な状態管理 |
| **Power Automate** | ①イベントトリガー (ファイル到着・メール・フォーム→エージェントWebhook)、②**HITL承認** (Teams/Outlookの承認ボタン)、③M365側の軽い後処理 | 多段分岐する業務ロジック本体 |
| **Power Apps** | 現場向けフロントエンド (依頼投入・承認キュー・実行モニタ) | ロジックの埋め込み |
| **Cursor AI** | 開発環境。ツールアダプタ開発・**VBS→Python移行**・テスト生成の生産性向上 | ランタイムの一部になること |

> 理由: Power Automate / Joule の中に業務ロジックを分散させると、
> ガードレール・監査・テストが効かない「野良自動化」が量産される。
> 判断と実行の中心を1箇所 (Python) に置き、他は入出力に徹させるのが
> 統制と拡張性の両立点。

## 3. SAP接続戦略 (最重要の技術判断)

転記業務の信頼性はSAPへの書き込み方法で決まる。優先順位:

1. **RFC/BAPI (PyRFC)** — 第一選択。トランザクション整合性 (BAPI_TRANSACTION_COMMIT)、
   構造化入出力、エラーが機械可読。例: `BAPI_ACC_DOCUMENT_POST` (会計伝票)、
   `BAPI_SALESORDER_CREATEFROMDAT2` (受注)、`BAPI_PO_CREATE1` (発注)
2. **OData / SAP Gateway** — BAPIが公開されていない場合。BTP経由なら
   Cloud Connector + Destination Service で安全にオンプレへ到達
3. **GUIスクリプティング (既存VBS資産)** — 上記が使えないトランザクション専用の過渡期手段。
   ただし扱いを変える:
   - VBSを**パラメータ化されたツール**としてPythonから起動 (引数はJSON→VBS)
   - 実行後は必ず**別経路で読み戻し検証** (GUIで書いた伝票をRFCで読んで突合)
   - 画面変更で壊れる前提でヘルスチェックを用意
   - **Cursorを使ってVBS→Python (pywin32 + SAP GUI Scripting API) へ順次移行**。
     同じGUI操作でもPython化すればログ・例外処理・テストがランタイムに統合できる

```
リスク別の書き込み経路の目安:
  金銭に直結する伝票 (支払/請求) → BAPI必須 (GUI経路は禁止)
  マスタ更新 (住所・銀行口座)     → BAPI推奨、GUI経路は読み戻し検証を厳格化
  参照系                          → RFC読み取り or OData
```

## 4. Joule の位置づけ

- Jouleは**SAP画面の中にいる人間**のためのアシスタント。定型質問・ナビゲーション・
  SAP標準機能の呼び出しに使う
- Joule Studio のカスタムスキルから **エージェント基盤のWebhookを叩く**ことで、
  「SAP画面内から『この伝票の消込を依頼』→ Python側で実行」という導線を作れる
- 逆方向 (エージェント→Joule) は作らない。エージェントはBAPIを直接叩くほうが確実
- BTPを使う場合の役割: Cloud Connector (オンプレ到達)、Destination (認証情報管理)、
  Event Mesh (SAPイベント→エージェントのトリガー)

## 5. HITL承認 = Power Automate 承認フロー

前プロジェクト (`src/support-agent/`) のHITL承認キューを、実環境では
**Power Automateの承認アクション**に置き換える。これが本スタックの強み:

```
Pythonエージェント: 高リスク操作を検知
  → PA承認フローをHTTPトリガーで起動 (何を・なぜ・diff・根拠を渡す)
  → 承認者のTeams/Outlookに承認カードが届く (モバイルでも決裁可能)
  → 承認/却下がコールバックでPythonに返る
  → 承認: 実行再開 / 却下: 有人対応へ / タイムアウト: 自動エスカレーション
```

承認履歴はPA側とエージェント監査ログの両方に残る (二重記録が監査対応に効く)。

## 6. 代表ユースケースの実行フロー

### 6.1 請求書処理 (SharePoint → SAP転記)

```
1. [PA] SharePoint「受領請求書」ライブラリに PDF到着 → Webhook
2. [Python] Claude (vision) でPDFから構造化抽出
   {vendor, invoice_no, date, amount, tax, line_items}
3. [検証] 決定的コードで: 金額計算の再計算一致 / 発注書(PO)とのマッチング
   (SAPからRFCでPO照会) / 重複請求チェック (invoice_no + vendor)
4. [リスク判定] 金額 ≤ 上限 & PO完全一致 → 自動 / それ以外 → PA承認
5. [転記] BAPI_ACC_DOCUMENT_POST → COMMIT → 伝票番号取得
6. [読み戻し検証] 伝票をRFCで読み直し、金額・勘定・消費税を突合
7. [記録] SharePoint台帳に結果行追記 + Teams通知 + 監査ログ
```

### 6.2 マスタ転記 (Power Apps → SAP)

Power Appsの申請フォーム → PA経由でWebhook → 申請者の権限確認 (コードで強制)
→ BAPIでマスタ更新 → 読み戻し検証 → 申請者へ完了通知。

### 6.3 月次レポート (SAP → SharePoint)

スケジュール起動 → RFCで試算表/明細抽出 → Python (pandas/openpyxl) で加工
→ Claudeが差異コメント草案を生成 (数値はデータから、文章のみLLM)
→ SharePointに保存 → Teamsに要約投稿。

## 7. ガードレール (支援エージェントの原則をそのまま適用)

`src/support-agent/policies.ts` と同じ構造をPythonで実装する:

| 原則 | 本スタックでの実装 |
|---|---|
| LLMは判断、実行はツール | 金額・伝票番号・勘定コードはLLM生成文から取らず、抽出結果を決定的コードで再検証してからBAPIに渡す |
| リスク階層 | L0: 参照 / L1: 可逆マスタ更新 / L2: 会計伝票・支払 → PA承認必須 |
| 本人・権限確認 | 申請者のAzure AD ID + 業務ロール表をコードで照合 (SoD: 申請者と承認者の分離) |
| 読み戻し検証 | SAP writeは全件。GUI経路のwriteはRFC読み戻しで突合 |
| 冪等性 | invoice_no等の業務キーで重複実行を遮断 (PAの重複トリガー対策) |
| 監査 | 全ツール呼び出しをDB + SharePointリストに二重記録 |
| 認証情報 | サービスアカウント最小権限。Key Vault管理。エージェントに人間のSAPアカウントを使わせない |

## 8. リファレンス実装

`python/backoffice_agent/` に本設計のランタイム骨格 (実行可能なプロトタイプ) がある。
モックアダプタで請求書処理フロー一式 (抽出→PO照合→リスク判定→承認→転記→読み戻し検証→監査) が動く。
実環境への移行はアダプタの差し替え:

| モック | 本番実装 |
|---|---|
| `adapters/sap_mock.py` | PyRFC (BAPI) / pywin32 GUIスクリプト / OData |
| `adapters/sharepoint_mock.py` | Microsoft Graph (Sites.Selected 最小権限) |
| `adapters/approval_mock.py` | Power Automate 承認フロー (HTTPトリガー + コールバック) |
| `llm_mock.py` の抽出関数 | Claude API (vision + structured output) |

## 10. リスクと対策

| リスク | 対策 |
|---|---|
| GUIスクリプトの脆さ | 新規はBAPI優先。GUI経路は読み戻し検証+ヘルスチェック+段階的廃止 |
| 野良自動化の乱立 | 業務ロジックはPythonランタイムに集約。PA/Jouleは入出力に限定するガイドライン |
| SAP権限の過大付与 | 業務別サービスアカウント + トランザクションコード単位の権限設計 |
| 抽出誤り (請求書OCR) | 計算再検証・PO突合・重複チェックの決定的バリデーション層で受け止める |
| M365ライセンス/API制限 | Graphのスロットリング対応 (指数バックオフ)、PAプレミアムコネクタ費用を事前試算 |
