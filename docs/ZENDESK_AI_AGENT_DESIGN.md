# Zendesk AI 自律型エージェント 設計書

L1 FAQ対応と転記業務（チケット→基幹システムへのデータ連携）を自律遂行する
カスタマーサポートエージェントのアーキテクチャ設計。

---

## 1. ゴールとスコープ

| 項目 | 内容 |
|---|---|
| L1 FAQ自動応答 | ナレッジベース (Zendesk Guide) に基づく生成応答で一次解決。目標: 問い合わせの40〜60%を自動解決 (deflection) |
| 転記業務の自動化 | チケットから構造化データを抽出し、基幹システム (ERP / CRM / スプレッドシート / 会員DB) へ自動転記。例: 住所変更、注文キャンセル、返金申請、契約プラン変更の受付処理 |
| エスカレーション | 自動解決できない/リスクの高い案件は文脈を引き継いで人間のエージェントへ |
| 非スコープ (初期) | 電話チャネル、多言語 (日本語のみで開始)、L2以上の技術対応 |


**設計方針: 「会話はZendesk、業務実行は自社オーケストレーション層」の二層構成。**

- **① Zendesk AI Agents (Advanced)** に会話・FAQ・情報収集を任せる。
  ノーコードの対話フロー + Guide連携の生成応答は内製するより速く、
  チャネル統合・引き継ぎ・CSAT計測が最初から揃っている。
- **② オーケストレーション層** は自社で持つ。転記業務は「どの基幹システムに
  何を書くか」という企業固有ロジックの塊で、ここにLLMエージェント
  (ツール使用ループ) + ガードレール + 承認フローを実装する。
  ※ このリポジトリの `src/agent-os/` (カーネル/ガードレール/ツールレジストリ) が
  この層のプロトタイプに相当する。

## 3. ユースケース別フロー

### 3.1 L1 FAQ (例: 「返品ポリシーを教えて」)

1. AI Agentがインテント `faq.*` に分類
2. Guide記事を検索 → 生成応答 (出典記事リンク付き)
3. 「解決しましたか？」確認 → Yes: 会話クローズ (チケット化しない) / No: 有人へ
4. 応答不能 (低確信度) の場合は推測で答えず即エスカレーション

### 3.2 転記業務 (例: 「住所を変更したい」)

1. AI Agentがインテント `procedure.address_change` に分類
2. **本人確認**: 会員番号+登録メールへのOTP等 (ポリシーに応じて選択)
3. **スロットフィリング**: 新住所を対話で収集、郵便番号APIで正規化
4. カスタムアクションでオーケストレーション層のAPIを呼ぶ:
   ```json
   POST /actions/execute
   {
     "intent": "address_change",
     "ticket_id": 12345,
     "entities": { "member_id": "M-0012", "new_address": "..." },
     "conversation_context": "..."
   }
   ```
5. オーケストレーション層のエージェントが実行:
   - 会員DBから現住所を照会 (read) → 変更内容の妥当性確認
   - **リスク判定**: 低リスク → 即実行 / 高リスク → HITL承認キューへ
   - 基幹システムAPIで更新 (write) → 結果検証 (書いた値を読み戻す)
   - Zendeskチケットに内部メモ (実行内容・監査ID) + タグ付与 + 解決クローズ
6. ユーザーへ完了通知 (AI Agent経由 or メール)

### 3.3 エスカレーション

- 引き継ぎ時にAI Agentが**会話サマリ + 収集済みエンティティ + 試行した操作**を
  チケットに添付 (エージェントが一から聞き直さない)
- SLA: 高優先度インテント (解約・クレーム・決済トラブル) は自動化を試みず即時有人

## 4. オーケストレーション層の内部設計

```
Webhook/API受信
  → タスクキュー (冪等キー = ticket_id + intent + hash)
  → エージェントプロセス起動
      ループ: LLM (Claude) がツールを選択・実行
        ツール例:
          zendesk.get_ticket / add_internal_note / update_ticket
          crm.lookup_member / crm.update_address
          erp.get_order / erp.cancel_order / erp.create_refund
          sheets.append_row
          kb.search (RAG: 業務マニュアル・過去対応事例)
          hitl.request_approval (高リスク操作)
  → 結果をZendeskに書き戻し + 監査ログ確定
```

主要コンポーネント (本リポジトリ `src/agent-os/` の対応物):

| コンポーネント | 役割 | agent-os対応 |
|---|---|---|
| タスクキュー + ワーカー | 冪等性・リトライ・同時実行制御 | Kernel / Scheduler |
| ツールレジストリ | 基幹システムAPIのラッパー群。インテントごとにアロウリスト | ToolRegistry |
| ガードレールエンジン | 後述 §5 | GuardrailEngine |
| コンテキスト組み立て | 会話履歴 + RAG (業務マニュアル) + チケットデータ | ContextManager |
| 監査ログ | 全ツール呼び出しの入出力を不可変記録 | EventLog |

**LLMは判断、実行はツール**: 金額・ID・住所などの値はLLMの生成文から取らず、
必ずツールの構造化入出力から取る。LLMが数値を「書き写す」場面を作らない
(転記ミスの根本対策)。

## 5. ガードレール設計 (最重要)

| レイヤ | ポリシー | 実装 |
|---|---|---|
| 認可 | インテントごとのツールアロウリスト。`address_change` エージェントは返金APIを呼べない | ツールレジストリで静的に定義 |
| 本人確認 | write系は認証済みセッション必須。未認証はread系も会員情報を返さない | オーケストレーション層で強制 (LLMの判断に委ねない) |
| リスク階層 | L0: 読み取りのみ→自動 / L1: 可逆的write (住所変更)→自動+事後通知 / L2: 不可逆・金銭 (返金・解約)→HITL承認必須 | アクション定義にリスクレベルを付与 |
| 金額上限 | 返金は¥10,000まで自動、超過は承認キュー | ツール実行前の決定的チェック |
| 入力防御 | プロンプトインジェクション検知 (顧客メッセージは常に「データ」として扱い、システム指示と分離) | コンテキスト組み立て時に封じ込め |
| 出力防御 | PIIリダクション、他顧客情報の混入チェック | 応答前フィルタ |
| 予算 | 1タスクあたりのLLM呼び出し回数・トークン上限 (暴走防止) | ステップ/トークン予算 |
| 検証 | write後に読み戻して意図した値になっているか確認。不一致は自動ロールバック+エスカレーション | ツール実行フローに組み込み |

## 6. HITL (Human-in-the-Loop) 承認フロー

- L2アクションは実行前に承認リクエストを生成: **何を・なぜ・根拠 (会話抜粋+照会結果)・実行内容のdiff** を提示
- 承認UI: Zendeskチケットのサイドバーアプリ or Slack (ボタンで承認/却下/修正)
- タイムアウト (例: 2時間) で自動的に有人対応へフォールバック
- 承認/却下の履歴は教師データとして蓄積 → 閾値チューニングと自動化範囲拡大の根拠にする

## 7. ナレッジ設計 (FAQ品質の土台)

- Guide記事を「1記事1トピック、結論先頭、手順は番号付き」に整備 (生成応答の品質は記事構造に直結)
- 記事にラベル付与 (インテントとの対応付け) で検索精度向上
- **ギャップ検出ループ**: 低確信度で答えられなかった質問を週次で集計 → 記事作成キューへ
- 業務マニュアル (転記手順・判断基準) はオーケストレーション層のRAGに投入し、会話用KBと分離

## 8. 可観測性とKPI

| KPI | 定義 | 目標 (6ヶ月) |
|---|---|---|
| 自動解決率 (deflection) | AIのみで解決した会話 / 全会話 | 50% |
| 転記自動化率 | 人手ゼロで完了した手続き / 対象手続き | 70% |
| 転記エラー率 | 検証NG or 事後修正が発生した割合 | < 0.5% |
| エスカレーション品質 | 引き継ぎ後に再ヒアリングが不要だった割合 | 90% |
| CSAT (AI対応) | 自動解決会話の満足度 | 有人対応と同等以上 |
| 承認リードタイム | HITL承認の平均待ち時間 | < 30分 |

ダッシュボード: Zendesk Explore (会話系) + 自社ポータル (転記実行・ガードレール検知・監査ログ) — 本リポジトリの `/agent-os` UIをそのまま発展させる。

## 9. 段階的ロールアウト

| フェーズ | 内容 | ゲート条件 |
|---|---|---|
| P0 (2-4週) | KB整備、インテント設計、Zendesk AI Agents導入、FAQのみ自動応答 | 自動解決率30% & 誤答クレームなし |
| P1 (4週) | オーケストレーション層構築、read-onlyツール (照会系: 注文状況・ポイント残高) | 照会精度99% |
| P2 (4-6週) | L1 write (住所変更等の可逆操作) を自動化、全writeにHITL承認 | 転記エラー率<1% |
| P3 (継続) | 承認実績に基づき低リスク操作を承認レスへ移行、対象手続きを拡大 | 週次レビューで判断 |

## 10. 技術選定の要点

| 論点 | 推奨 | 理由 |
|---|---|---|
| 会話AI | Zendesk AI Agents (Advanced) | チャネル/引き継ぎ/CSAT内蔵。対話フローの内製は工数対効果が悪い |
| 業務実行 | 自社オーケストレーション層 (Node/TS + Claude API) | 企業固有ロジック・ガードレール・監査の完全な制御が必要 |
| Zendesk連携 | Webhook + REST API (+ ZISは軽量な同期に限定) | ZISだけで複雑なエージェントループは組めない |
| LLM | Claude (tool use) | 多段ツール使用の信頼性、日本語品質 |
| 状態管理 | タスクキュー (冪等) + PostgreSQL | Webhookは重複配送前提で設計 |

## 11. 主要リスクと対策

| リスク | 対策 |
|---|---|
| 誤転記 (最重大) | LLMに値を書き写させない設計 (§4) + 書き戻し検証 + L2はHITL |
| 誤案内 (FAQ誤答) | 低確信度は回答せずエスカレーション。出典記事リンクを常に添付 |
| なりすまし | write系は本人確認をコードで強制。LLM判断に委ねない |
| Webhook重複/欠落 | 冪等キー + 定期リコンシリエーション (未処理チケットの掃き出し) |
| ベンダーロックイン | 業務ロジックを②に集約しておけば、①は差し替え可能 |
